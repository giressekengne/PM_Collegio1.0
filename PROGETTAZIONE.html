1. Introduzione

Questo documento raccoglie la documentazione di progettazione del sistema PM_Collegio v2 : l'architettura, i diagrammi UML (casi d'uso, classi, sequenza, stati) e il diagramma ER del livello di persistenza. Completa la Specifica dei Requisiti (SRS) : dove la SRS dice cosa il sistema deve fare, questo documento descrive come è strutturato per farlo.

I diagrammi sono stati ricavati dal codice sorgente del progetto (package it.collegio.*) e dallo schema MySQL di riferimento ; ogni identificativo di requisito citato (RF-n, RNF-n, RI-n) rimanda alla SRS versione 1.0.

2. Architettura del sistema

PM_Collegio v2 adotta un'architettura a strati ispirata al pattern MVC, integrata con DAO per l'accesso ai dati e DTO per il trasporto di dati joinati. La regola fondamentale (RNF-1) è la direzione delle dipendenze : una View non parla mai con il database, ma solo con un Controller ; il Controller orchestra i DAO ; solo i DAO eseguono SQL, prelevando le query da QueryContainer (RNF-2).

Fig. 2.1 : diagramma dei package, con la direzione delle dipendenze tra layer.

I package utilities, enums e config sono trasversali : QueryContainer centralizza le query SQL, SessionContext mantiene lo stato della sessione corrente, i tipi enumerati codificano gli stati del dominio (camera, prenotazione, fattura, utente), db.properties esternalizza le credenziali (RNF-8, letto da DatabaseConnection all'avvio).

3. Diagramma dei casi d'uso

Gli attori sono i quattro ruoli del sistema : Cliente (U), Receptionist (AR), Admin committente (AC), Admin di sistema (AS). La generalizzazione AS → AC indica che l'admin di sistema può svolgere tutte le operazioni dell'admin committente, su qualunque committente.

Fig. 3.1 : diagramma dei casi d'uso. Il check-in e il check-out includono l'emissione della fattura (RF-21, RF-26).

4.1 Modello di dominio (vista compatta)

Le 12 classi del package it.collegio.models sono POJO in corrispondenza 1:1 con le tabelle del database (RNF-3). La vista è compatta : il dettaglio degli attributi è nel diagramma ER del Cap. 7.

Fig. 4.1 : modello di dominio. Per leggibilità sono omesse le associazioni multi-committenza di Room, Reservation e Sessions verso Committente, Sessions verso Mansione, StoricoPrenotazioni verso User e il ruolo «gestore» di Committente verso User : sono tutte riportate nel diagramma ER (Fig. 7.1).

4.2 Spaccato MVC : il sottosistema Fatture

Lo spaccato mostra come un sottosistema attraversa i layer : due view condividono lo stesso controller, che orchestra tre DAO ; i dati joinati viaggiano nel DTO FatturaDettaglio, che include reservationStato per la regola di pagabilità combinata (RF-30).

Fig. 4.2 : spaccato del sottosistema Fatture. I DAO costruiscono i DTO dai ResultSet delle query joinate ; lo stesso schema (View → Controller → DAO → DTO) si ripete in tutti i sottosistemi.

7.2 Note di progettazione della persistenza

  • Chiave applicativa : User.user_counter è VARCHAR(100) nel formato XXX{id}{NOME}, generata da UserDao.generateUniqueCounter() con retry su collisione (RF-10). Non è un AUTO_INCREMENT.
  • ENUM ↔ enums Java : le colonne ENUM di MySQL (stato camera, prenotazione, fattura, utente) sono mappate 1:1 sui tipi del package it.collegio.enums ; la conversione avviene nei DAO.
  • Vincolo logico fattura : la relazione Fattura-Reservation è 0..1 applicativa, garantita dall'upsert del check-out, non da un vincolo UNIQUE sul DB.
  • Multi-committenza : committente_id è presente su User, Room, Reservation e sessions (RNF-17) ; l'esercizio attuale usa il solo committente 1 (VG-4).
  • Credenziali : i parametri di connessione vivono in db.properties fuori dal repository (RNF-8) ; DatabaseConnection li carica dal classpath in un blocco statico.
  • Dati di seed : lo script DDL include mansioni, indirizzi, committente 1, utenti e metodi di pagamento, presupposti dal sistema al primo avvio (P-2 … P-5 della SRS).
